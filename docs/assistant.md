# Yoru, the assistant

Decided on 2026-10-19. Yoru becomes a personal assistant that lives on the computer, and the round ESP32-S3 board (`../yoru`) is its body. It connects to the services you use (mail, calendar, documents, issues…) through MCP connectors, tells you when something worth knowing happens, and answers when you ask: "anything new?", "what's on tomorrow?", "find the mail from…".

This repository (`yoru-hub`, formerly `companion-hub`) becomes Yoru's only host program. DualEye leaves it (DualEye keeps its own `host/`). The Yoru app (`../yoru-app`, the fork of coucou) was retired on 2026-10-19, once phase A2 worked.

Out of scope, on purpose: firmware 0.9's remote features on the host (drafts, session chats, new sessions), following coding agents (see below) and the Mac-native parts of the Yoru app (pasting with Accessibility, bringing a terminal to the front, Parakeet, Apple's speech recognition). The board still works without them: its push-to-talk is an ordinary utterance.

## Connectors: our MCP client

Yoru is an MCP **client** of the services' servers, and stays an MCP **server** for Claude Code (`mcp.rs`).

`rmcp` 3.5 (already a dependency, server side only) has the client side too: the features `client`, `auth`, `transport-streamable-http-client-reqwest` and `transport-child-process`. Its `auth` module does the OAuth 2.1 work: discovery of the server's metadata, dynamic client registration, PKCE, token refresh and scope upgrades, behind a `CredentialStore` and a `StateStore` trait.

New in `core/src/connectors/`:
- `store.rs`: `CredentialStore` and `StateStore` on the system keychain (the `keyring` crate). Tokens never go into a plain file.
- `login.rs`: the OAuth redirect on a loopback address (`http://127.0.0.1:<port>/callback`, RFC 8252). It opens the browser, takes the code, and closes.
- `registry.rs`: the connectors in `connectors.json` in the data folder. Each one has its transport (a URL, or a command for a local server), a client id and scopes when the service needs our own, the tools turned on, and for each tool whether it only reads or acts.
- `manager.rs`: a tokio runtime on a thread of its own. It keeps the MCP sessions open, reconnects them, refreshes tokens, and lists the tools of every connector. The agent is synchronous (`ureq`, threads), so it reaches the manager through a blocking handle.

There are three kinds of service:
- **A remote MCP server with dynamic registration.** It works with nothing set up in advance. Several services publish one; whether each supports dynamic registration is checked service by service.
- **A service that needs our own OAuth client**: GitHub, Slack, Box, Asana, HubSpot (none takes dynamic registration or client ID metadata documents, checked 2026-10-19). The app's own client for each is registered once and compiled in from `YORU_<SERVICE>_CLIENT_ID`/`_SECRET` (`docs/oauth-clients.md`), so Connect is one click there too. A build without it falls back to the user's own client, folded under "Advanced" on the card.
- **Google (Gmail, Calendar)**: since 2026-10-22 Yoru Hub serves their tools itself, on the REST APIs, with a "Desktop app" client the user makes in their own Google Cloud project (`docs/oauth-clients.md`). A client of ours would need Google's verification for Gmail's restricted scopes; the user's own works with any account. Drive is left out for now.
- **A local MCP server** (`npx …`, `uvx …`), run as a child process, with its token in the keychain and passed as an environment variable.

Web search on every brain comes from Tavily (`tavily` in the catalog, added 2026-10-21): a remote server with dynamic registration, whose free plan gives 1,000 credits a month (a basic search costs 1, an advanced one 2). Its tools carry no read-only annotations, so the preset marks search, extract, crawl and map as reading; `tavily_research` (4 to 250 credits a call) and `tavily_feedback` start turned off. A watcher on `tavily_search` with `topic: "news"` and `time_range: "day"` follows a subject without the model; feeds stay the better source for fixed headlines, since they cost nothing. Exa (`exa`, added 2026-10-22) is a second search with no sign-in; Airtable, ClickUp and Miro joined the catalog the same day, all with dynamic registration.

## The agent

`agent.rs` already has the loop: tools, their results fed back, a short memory, a provider with a local fallback. What changes:
- **A model that can handle many tools.** A provider for Anthropic's Messages API next to the OpenAI-compatible one (`cloud/`). The local model stays for quick and offline requests.
- **Five brains.** The user picks one (`provider` in `assistant.json`; unset: the first with a key of Claude, OpenAI, Google and Groq; Ollama only when picked), see "The brain" below.
- **Tools at once.** The tool calls of one round on Groq, OpenAI, Google and Ollama (but `find_tools` and `load_tools`) run at the same time since 2026-11-08: two web searches take as long as the slower.
- **Tools on demand.** Yoru's own (`notify`, `remember`, timers) and the board's essentials (`react`, `get_state`) are always there; a connector's tools and the board's other ones (volume, brightness, wake word, menu, settings) only once the model looks for them (tool search on Claude, `find_tools` and `load_tools` on the other brains). With many services connected, a request doesn't carry every tool of every connector.
- **Acting asks first.** A tool marked as acting (send a mail, create an event, close an issue) shows on the board's approval card (`show_approval`, already in the firmware) and in the app, and runs only on Allow. Reading never asks.
- **Longer turns.** More rounds and tokens than a voice command; the spoken reply stays short, and the full answer is kept in the conversation in the app.
- **Who Yoru is.** Every brain gets the same short identity (`assistant::identity`): his name, an AI assistant that lives on the user's desk (the board or the Mac's notch), male, and one fixed tone: clear, concise and courteous, with no backstory, feelings or moods of his own, and no jokes or small talk unless asked. It goes into the assistant's system prompt (`mod.rs`, `compat.rs`), Gemini Live's (`live.rs`) and the model on this Mac (`agent.rs`).

## The brain

Decided on 2026-10-19: Yoru thinks with one of two brains, so people can start without paying. On 2026-10-20 OpenAI (paid, cheap) and Ollama (a model on this computer, free and private) joined Groq in `assistant/compat.rs`, the turn for every brain that speaks OpenAI's chat completions. They differ in a budget (`compat::Budget`): Groq and Ollama get the tight one below (Groq counts the answer's reserved tokens against its 8K a minute, and a local model reads a short prompt best), OpenAI a roomy one (16 connector tools, the memory to 12,000 characters, the last 10 turns, results to 30,000 characters, 4,096 tokens an answer).

- **OpenAI** (`openai_model`, `gpt-6-luna` by default; `gpt-5.4-mini`, `gpt-5.6-terra`). Only models that call tools through Chat Completions: they do it with `reasoning_effort: "none"`, and want `max_completion_tokens` instead of `max_tokens`. GPT-6.1 Sol and Astra call tools only through the Responses API, which Yoru doesn't speak. Its key serves `whisper-1` too.
- **Google** (`google_model`, `gemini-4-hydrogen` by default; `gemini-3.5-flash-lite`, `gemini-3.6-flash`, `gemini-3.8-flash`, and the paid-only `gemini-4-argon` and `gemini-4-carbon`), added 2026-11-13 through Google AI Studio's OpenAI-compatible API (`generativelanguage.googleapis.com/v1beta/openai`, key in `GEMINI_API_KEY` or the app). The roomy budget, like OpenAI: the free tier counts requests a minute and a day, not Groq's few tokens. Gemini 3 and 4 always think a little, so they get `reasoning_effort: "low"` and at least 4,096 `max_tokens` (the thinking counts against it). Their tool calls carry a thought signature (`extra_content.google.thought_signature`) that has to go back with the call: the stream keeps it, and a call without one (none should be, since changing the brain starts a new conversation) gets the stand-in `skip_thought_signature_validator` Google allows. Google's errors come as `[{"error": …}]`; a 429's `RetryInfo` and `QuotaFailure` say when to retry and whether the day's quota ran out, a wrong key is a 400. No web search but Tavily: Gemini searches only through its own API's grounding. Its keys also go to the board for talking without the hub, as a plain chat without tools.
- **Ollama** (`ollama_model`, empty until the user picks one of the models Ollama lists at `/v1/models`). No key; `http://localhost:11434/v1`, or `OLLAMA_BASE_URL`. The model must support tools.

| Connector tools | none loaded at first (but Tavily's search, see below): the prompt names the connected services (a line each), the model searches their tools with `find_tools` (names and a line each, ranked by `assistant/select.rs`: BM25 over service, name and description, with a few Italian words mapped to English) and loads the ones it wants with `load_tools`; 6 stay loaded at most (16 on OpenAI and Google), the oldest go first, and those the conversation used stay for follow-ups | all of them, deferred behind server-side tool search |
| Web search | only through the Tavily connector: Groq's compound models aren't used, OpenAI searches only through the Responses API, and without Tavily the model is told it can't search. Since 2026-11-14 a query about the news ("notizie", "news", "novità", "ultime"…) goes to Tavily's `news` topic with 6 results, today's (`time_range: day`) when it says today, else the week's: the general search for "notizie 14 novembre 2026" had found a news site's tag page and the answer was empty. The model is also told that current facts come only from a search made for the question (asked again, it searches again), to answer with what the results say (for the news the three or four main stories) and nothing more, and not to end with questions or small talk | the server tool |
| Prompt | a compact system prompt, the memory cut to 3,000 characters, the last 4 turns, tool results cut to 6,000 characters, tool descriptions to 300, 1,024 tokens an answer (2,048 for a triage) | the full prompt, cached |
| Triage | structured output (`response_format: json_schema`, strict) for OpenAI, Gemini, GPT-OSS and Qwen; JSON mode with the schema in the prompt for Llama and Ollama | `output_config.format` |

The conversation is kept in memory in the brain's own form (Anthropic's content blocks or OpenAI's messages); changing the brain starts a new one. The saved log (`conversation.json`) is the app's neutral `ChatLine`s, so nothing old breaks.

A 429 from Groq says what ran out (the minute's tokens or the day's) and when to retry (its `retry-after`, or the "try again in 7m12s" of its message). The model isn't asked again until then. The app shows it as an error with that time; said to the board, Yoru answers with a short spoken line ("I've used up today's free thinking. Try again in 13 minutes.") instead of a worse answer. Tests point Groq elsewhere with `GROQ_BASE_URL` (each provider's key variable with `_BASE_URL`), as `ANTHROPIC_BASE_URL` does for Claude.

The first run's brain step offers Groq, Gemini, OpenAI and Claude, with their keys (Ollama is picked later, in Settings); its optional second part sets Yoru's voice: an ElevenLabs key, one of the account's voices (`elevenlabs:voice/<id>`, for both languages), and a test on the board. Settings has the five brains, their keys and their models (and Ollama's thinking switch); `yoru settings provider …` and `yoru settings groq_model …` do the same from the CLI.

## Voice

The board streams what it hears after its wake word, with PWR held, or while it keeps listening after an answer (`core/src/voice.rs`).
- **Listening.** whisper.cpp's `whisper-server` on this computer (`stt.rs`, Whisper `base`, `small` or `large-v3-turbo`), or a provider's Whisper (Groq, OpenAI), falling back to the local one at the provider's limits. Italian or English, detected.
- **Speaking.** Piper on this computer (`tts.rs`, a voice per language), or a provider's voice: ElevenLabs (it acts out audio tags such as `[laughs]`) or Groq. A failed cloud voice hands over to a downloaded one for a minute. What ElevenLabs said is kept, one clip per sentence, on the Spoken page (`spoken.rs`), to play again or export as a zip; Gemini Live's answers are kept there too, one clip per answer (its voice at 16 kHz and what it said), under their own source (`gemini-live:<voice>`) and their own tab, never mixed with ElevenLabs'. Tests replay only ElevenLabs' clips on the board with `host/say` and `"recorded": true`, a clip per sentence, so as not to spend credit; real answers always ask the voice. Everything each board and the notch do (connections, the board's log, what was heard, transcribed and answered and by which brain, Gemini Live opening or staying silent, voice errors, the notch's push-to-talk and microphone, a voice pipeline that stops, and any crash with its backtrace, tagged `panic`) goes to `yoru.log` in the data folder (`hostlog.rs`), one timestamped line an event tagged with the board's port, `mac` for the notch; at 2 MB it starts over, keeping `yoru.log.1`. Each spoken answer adds a line to `voice-times.log` in the data folder, and to the board's log: how long the board waited for the end of the sentence, the transcription, the brain's first words and first sentence, the whole answer, the first sound and the voice's own wait, and the tool rounds. The brain adds its own line for every answer on Groq, OpenAI, Google or Ollama, voice or text: each round's model time and the size of what was sent, and each tool's time.
- **Keep listening after an answer.** The board listens again without the wake word, for as long as the answer calls for (`voice/listen` with `wait_ms` and `pause_ms`). What is heard then may only close the conversation ("no, thanks") or acknowledge it ("ok"): fixed phrases, or EmbeddingGemma on a `llama-server --embedding` sidecar (`intent.rs`) telling a goodbye from a new request; anything else goes to the assistant.
- **When you finished.** A short pause on the board, or Pipecat's Smart Turn v3.2 (`turn.rs`, run with tract) hearing from the voice whether the sentence is finished, on each `utterance_pause`, then `voice/stop`.

- **On the Mac.** Yoru in the notch is a board made of software that hears through the Mac's microphone and speaks through its speakers, push-to-talk on ⌥ Space ([notch.md](notch.md)).

### Gemini Live

Added 2026-11-13, off by default (Voice page, "Gemini Live", a voice to pick; needs a Google key and listening on). Gemini Live hears the request, thinks and speaks in one model, over a WebSocket (`cloud/live.rs`, `BidiGenerateContent`), instead of Whisper, the brain and the voice one after another.
- **The session.** Opened at the first utterance and kept for the follow-ups and for any utterance up to 15 minutes after the last turn (as long as the other brains' conversation), so a second press of push-to-talk goes on with what was said; Google may close it sooner, and then the turn goes to a new one. Its setup is fixed when it opens (`Assistant::live_setup`, `assistant/live.rs`): a short spoken prompt without face or audio tags, the memory's core, the reply language, Yoru's own tools, the timers and the board's essentials, and Google Search when web search is on. The services' tools aren't there (too many to send them all), nor the facts recalled per request. Tool calls run through the same tool runner and confirmations (`Assistant::live_call`). Automatic voice detection is off: the board says when the utterance starts and ends (`activityStart`, `activityEnd`). Live's own transcript of the user is poor (Thai or Chinese for an Italian «ciao», made-up words) even when it understood, and takes no language hint: the utterance also goes, beside the turn, to Gemini 3.5 Transcribe (`gemini-3.5-transcribe-live`, `live::transcribe`) on the same key, a Live API model that only writes down speech, free with no daily limit (20,000 tokens a minute), with the reply language as its `languageCodes` (Italian and English when automatic) and «Yoru» as custom vocabulary. On the recordings where Live and OpenAI's `whisper-1` both went wrong it got every sentence right, in 1.3 to 2 s. It writes while the user speaks (`live::Scribe`): its connection opens when the board starts streaming, the audio goes in as it comes, and Google sends drafts of what was said so far (`interimInputTranscription`, about half a second behind the voice) before the final text (`inputTranscription`, 0.2 to 0.5 s after `activityEnd`). Each draft goes to the app as a `Hearing` event (`hearing` to the windows), which the notch and the Conversation page show as the user's line being written until the real line arrives. If the scribe failed (it opens as the user starts), the whole utterance is written at its end as before. Its text is what the conversation and the memory keep; without a Google key Yoru's speech-to-text writes it, and if that fails Live's own stays. It is shown as soon as it's written (`Assistant::live_heard` puts the user's line in the conversation, and the transcript goes to the app), while Live is still answering; Live's own transcript is shown only at the end of the turn, when the other one failed.
- **Streaming.** Google takes the audio in real time, so the board's frames go out as they arrive (`Hearing::Audio`); sent whole at the end, the answer waited for as long as the sentence lasted. Measured: 1.1 s from the end of the sentence to the first sound, 1.6 s with a tool call. The answer comes as 24 kHz PCM, brought to the board's 16 kHz (`live::Downsampler`) and played as it arrives; Google's transcriptions of both sides go to the app's conversation and the memory's episode (`Assistant::live_turn`).
- **Speed.** Live hears the words as they're spoken, so nothing else may hold the voice pipeline's thread meanwhile: the local model isn't primed when Live answers (priming it takes seconds and kept the words queued), and a board that sends `about_to_talk` (the notch, when the pointer comes onto it) gets its session opened ahead, waiting up to three minutes for the next conversation. The rest of the wait is Google's: on `gemini-2.5-flash-native-audio` the first sound comes 1.3 to 2.6 s after the end of the sentence, now and then much later.
- **Models.** `gemini-3.8-live` first, then `gemini-3.1-flash-live-preview`, then `gemini-2.5-flash-native-audio-preview-12-2025` (thinking off). A model refused for its free limit isn't tried again for an hour (`yoru.log` says which and why); if none opens, or a turn fails before any sound, Yoru answers with the usual pipeline and doesn't try Live for ten minutes.
- **The voice.** Any of Google's 30 prebuilt voices, grouped in the app as male and female (Puck by default). Its answers go to the Spoken page under Gemini Live, apart from ElevenLabs'.

## The board's apps

The board has apps in its menu that the host drives:
- **Timers** (`set_timers`, `timer_action`). Each board's session (`bridge/session.rs`) sends the whole list from `timers.rs` whenever it changes (`Timers::revision`), and on every handshake; the board counts down by itself. A tap there pauses, resumes or dismisses one, a long press cancels it (`Timers::act`). The board also starts timers of its own (its Timers app, offline voice commands) and offers them with `timer_new`; `Timers::adopt` takes each over (a pomodoro's phase brings its pomodoro) and keeps the board's id as `was`, which the list sends back so the board drops its copy.
- **Tasks** (`set_tasks`, `task_run`, the `tasks` capability; they replaced the Habits app on 2026-11-03). Each session sends the board the tasks (`Tasks::board_list`: at most 8, texts cut to the board's fields, times in Unix seconds, whether each is running or failed last time) on every change, a run starting or ending included, and every ten minutes. "Do it now" on the board comes back as `task_run`; `Tasks::ask_run` queues it and the scheduler does it at once, with the board and the cards (see Tasks below). The snapshot's `host` carries the Mac's time zone (`tz`, from `/etc/localtime`, `presence.rs`), so the board's own clock keeps local time.
- **Talking without the hub** (`cloud/set`, the `cloud` capability). Each session (`bridge/session.rs`, with `bridge/cloud.rs`) sends the board the online services the voice uses, with their keys: the voice's cloud Whisper (else Groq's or OpenAI's), the assistant's brain unless it's Ollama (Claude, GPT, Gemini, Groq) and the cloud voice of the answers' language (ElevenLabs, Orpheus), plus the assistant's name and the memory's graph in short (`Memory::board`, 1,200 characters at most, see `docs/memory.md`). It checks every 30 s and sends only what changed; with one of the three missing it sends `{"clear": true}`. With the Mac away the board then transcribes, thinks and speaks on its own, the brain's tags acting on its timers and volume, with the tasks in its prompt (the firmware's `docs/protocol.md`, Cloud voice). The keys travel only on USB or the sealed WiFi link of a paired board, and the board keeps them in its flash.
- **Errands** (`show_fetch`). Each call the model makes to a connector's tool (not the watchers' calls) is told to `bridge/errands.rs` (`Assistant::set_errands`), which shows it on every board on a thread of its own: `start` before the call, `done` or `failed` after it, with the service's name. Each carries a `kind` that picks Yoru's animation: `fetch` (the portal) for a connector's tool that reads, `send` for one that acts, `search` for a web search (Claude's, its start seen in the stream as `Delta::Search`, its end with the answer; Tavily's since 2026-11-08, source `Web`, two at once when the model searches two topics), `remember` / `forget` for the memory tools and `note` for a change to the tasks or the timers; those last three are over at once and sent as `start` and `done` together.

## Memory

Since 2026-11-08 a graph of people and facts (`memory.db`), searched for each answer and consolidated after each conversation, with voice prints: [memory.md](memory.md). Before, it was a file (`memory.md`), imported into the graph once.

## Proactive: watchers, triage, notifications

- **Watchers.** A periodic check without the model: it calls a connector's read tool with fixed arguments ("unread mail since…", "events in the next 2 hours"), compares the ids with the ones already seen, and wakes the model only for new ones. A watcher is data: connector, tool, arguments, where the id is, how often.
- **Triage.** The model decides, with the memory, whether something new is worth telling, how urgent it is, and says it in one line.
- **Delivery** (`bridge/alerts.rs`). Every notification goes into the app's inbox and, with `show_notification`, into the board's at its urgency: `low` only in the inbox, `normal` with a banner and a chirp, `high` with Yoru knocking on the glass, `urgent` with the alarm, lighting the dark screen, and said aloud by the board that speaks once no conversation is on. In quiet hours anything below `urgent` arrives as `low`.
- **Feedback** (added 2026-11-13). Few right notifications are worth more than many: an opened notification on the board ends with Useful and Enough, which send `notification_action` `useful` or `enough`. `memory/verdicts.rs` keeps each verdict (`verdicts` table: source, watcher, title); Enough also writes a "Don't tell me about" fact. The triage reads the watcher's last verdicts with the memory and tells more like the useful ones, none like the others; and a source (a watcher, or a source name without one) with at least two Enough in the last 30 days, more than its Useful, is delivered a step quieter (`high` to `normal`, `normal` to `low`; `urgent` untouched).
- **Routines.** The morning recap (mail, calendar, what's pending) at a set time, and on request ("recap").
- **Tasks** (added 2026-11-03, in place of the user's habits, which were removed then). `assistant/tasks.rs` keeps in `tasks.json` the jobs the user gives Yoru, in words: once (a date and a time), every day or on some weekdays, on a day of every month (the month's last day when it is shorter), or every 1 to 168 hours. The scheduler runs a due one as a job of its own (`tasks::run`, through `Assistant::run_task`), which ends with a notification tagged with the task; what Yoru says he did is kept as its last result. A time missed while the computer was off is still done within 6 hours, later it is counted as missed; a new schedule, or a task turned back on, counts from then. Each task says how far it may go: read and tell (anything that acts is refused), ask first (the board's Allow/Deny card and the app's, as in a conversation; unanswered, not done) or act without asking. Only the app sets the last one: the model's `tasks` tool (list, add, disable, enable, remove: disabling keeps a task, removing deletes it) always adds "ask first" tasks, so a mail a task reads can't set up one that sends freely. The app has a Tasks page with "do it now", the board a Tasks app (see "The board's apps"); the CLI's scheduler runs them too, unable to ask.
- **Firmware.** An inbox on the board: a `show_notification` tool (source, title, one line, urgency) and a list to scroll; `notification_action` comes back when it is read or opened, and with the user's verdict (`useful`, `enough`).

## Coding agents

Removed on 2026-10-21: Yoru no longer follows Claude Code. The hooks, the status line, the sessions' feed, the permission requests answered from the board or the app, the alerts about Claude ("Claude needs you", "Claude is done", the plan's limits) and the transcripts' usage are gone, and so are the board tools and notifications that served them (`set_agents`, `show_toast`, `show_question`, `hide_question`, drafts, chats, new sessions, `answer`, `shortcut`, `to` on `utterance_start`).

What stays:
- Yoru's MCP server (`mcp.rs`), for any MCP client, and the button that adds it to Claude Code's config (`claude/mcpconfig.rs`). A client can make Yoru react, speak, notify you and set timers.
- The Allow/Deny card (`show_approval`, `hide_approval`, the `approval` notification), now only for the assistant's own confirmations (`assistant/confirm.rs`, `bridge/confirm.rs`).

### Working the agents by voice (the `code_*` tools, since 2026-11-13)

Yoru doesn't follow the agents' hooks any more, but he can work them: `assistant/coding/` gives every brain (Gemini Live included) four tools for Claude Code, Codex and OpenCode on this computer. They were one tool, `code`, with an action, until Gemini Live answered "start a Claude session that tells me a joke" by calling its listing, and then said it had sent it: nothing ran and nothing ever came back. Each job now has its own tool, and `code_send` is described as the only way to have an agent do anything.

- **`code_send`**: the prompt, in the user's words, to an agent in the background. With `session` it continues a conversation (in its folder); with `run` it answers or continues one of Yoru's runs (one that ended with a question); with `project` (a folder, or a name matched against the folders of the user's conversations, `rome maps` finds `RomeMaps`) it starts a new one there; with none, a new one in a fresh folder, `~/Documents/Yoru Code/<date>/<the prompt's first words>`. A conversation a run of Yoru's is still working in isn't sent to again. Claude Code runs as `claude -p --output-format stream-json --verbose --permission-mode auto [--allowedTools …] [--resume <id>]` (its auto mode: it works on its own and risky actions are checked and refused); Codex as `codex exec [resume <id>] --skip-git-repo-check --json -c sandbox_mode="workspace-write" -o <file>` (the ChatGPT app's own `codex` when it isn't on the PATH); OpenCode as `opencode run --format json --auto [--session <id>] --model <provider/model#variant>` (`--auto` approves what its configuration doesn't deny). OpenCode is given the model of the conversation, else the one last used in that folder, else anywhere: its own default may be one its provider can't run (a Bedrock model without an inference profile). Every agent gets `PWD` set to its folder, since OpenCode works where `PWD` says, not in the process's folder, and the PATH of the user's login shell, since the app started from the Finder has a bare one. A run is stopped after an hour.
- **Following a run**: what the agent prints is read line by line as it comes (Claude Code's `stream-json`, the others' JSON events): the conversation's id as soon as it has one, and its steps in a few words (`ran cargo build`, `edited main.rs`, `searched the web for …`), the newest 6.
- **When a run ends**, Yoru says it out loud, in the language the user asked in, once the board is out of any conversation (the alerts thread, `AlertInput::Say`), and the line shows in the app's conversation; in quiet hours it is only written. Done: what it answered, whole sentences up to 240 characters with markdown and code left out, "the rest is in the inbox" when cut. It ends **needing the user** (`needs_you`) when Claude Code was refused something (`permission_denials`: "it asks permission for npm install, shall I let it?"), when Codex's sandbox stopped a command (`Operation not permitted`), or when its answer ends with a question ("Claude Code asks you: …"). Failed: why, and a login that ran out says how to log in again. The answer also goes to the inbox (source Claude Code, Codex or OpenCode, title `<folder>: done`, `needs you` at high urgency, `it didn't work`).
- **`code_status`**: with nothing, what is being worked on now (`Coding::active`): Yoru's runs, going or ended in the last 10 minutes, and every conversation of any agent written to in the last 3 minutes, the user's own included; the first 6 are looked inside. With `run` or `session`, what is going on inside it: its state, what it was asked, its last steps, what it last said, and for a run its answer and what it needs. A conversation is read from the agent's own files (`coding/peek.rs`: the last 768 KB of a `.jsonl`, OpenCode's `session_message` table): `working`; `waiting`, a step started over 45 seconds ago with nothing written since (an approval in the agent's window, or a long command: approvals aren't written anywhere, so it's a guess and Yoru says "maybe"); `your_turn`, it finished (Claude Code's `end_turn` or its stop hooks' line, Codex's `task_complete`, OpenCode's `idle`, or an answer with nothing after it for 15 seconds); `interrupted`. Codex's app works through scripts (`exec`) that call its tools; the step is the first tool the script calls.
- **`code_sessions`**: the user's conversations, newest first, read from the files they keep (`~/.claude/projects/<folder>/<id>.jsonl`, with the title the app gave it or the first message; `~/.codex/sessions/.../rollout-*-<id>.jsonl`, titled by `~/.codex/session_index.jsonl`; OpenCode's `~/.local/share/opencode/opencode.db`, opened read only, tables `session_v2` and the older `session`). The newest 60 of each are read; subagents' conversations, OpenCode's archived ones and conversations in scratch or temporary folders are left out. A query keeps those whose title, folder or id have its words. It says nothing of whether they're active, which Gemini Live once took them for.
- **`code_control`**: `approve` continues a run that needs an approval, allowed to do what it was refused (Claude Code: `--allowedTools`, a refused command as `Bash(<command>)`; Codex: `sandbox_mode="danger-full-access"` for that turn); only after the user said yes. `stop` kills a running run. `watch` keeps an eye on a conversation of the user's own, looked at every 5 seconds for up to 4 hours: Yoru says when it finishes (its last answer, or the question it ends with) and, once, when it seems to wait for the user; `unwatch` stops.

The app's Today page ("Agents at work") and the open notch show the active list, looked at every 5 seconds (`coding_active`, cached for 4); a run of Yoru's shows its last step and has a button to stop it (`coding_stop`), and one that needs the user says so. Closed, the notch shows how many are working when nothing else is waiting.

Every brain's prompt says never to claim something was done (sent, started, added, saved) unless the tool that does it said so: Gemini Live once told the user it had sent a request to Claude, and that it was running, without calling `send`.

It doesn't talk to the agents' apps: a conversation open in the Claude, Codex or OpenCode app doesn't show what Yoru sent until it is opened again. The `claude` command has its own login, apart from the Claude app's.

## The app: Yoru only, redone

Until 2026-10-19 the window was DualEye's: a home with the board's mirror and pills, and a settings drawer with Voice, Timers, Claude, Device and Diagnostics tabs. The new app has a sidebar:

| Page | What is on it |
|------|---------------|
| Today | Yoru's mirror, small; what it told you today; what comes next (events, timers); a field to type or talk to it |
| Conversation | The chat with Yoru, text and voice, with the tools it used folded away and the confirmations it is waiting for |
| Inbox | Every notification with its source, read or not, and its actions: open, reply, dismiss, "don't tell me about this again" (which goes into the memory) |
| Connectors | A card per service: connected or not, Connect and Disconnect, what it may read and what it may do, its watchers and how often |
| Tasks | The jobs you give Yoru, once or on a schedule, how far each may go, when it runs next and what it did last (added 2026-11-03) |
| Routines | The morning recap, quiet hours, the watchers' schedule |
| Memory | What Yoru knows about you, editable |
| Spoken | What ElevenLabs said, to play again, delete or export (added 2026-10-22) |
| Settings | A list of parts: how Yoru thinks and talks (a setup: Free, The best, Live, Private, or Custom with the brain, its model and key), the MCP server, voice (listening, speaking, keep listening, a goodbye, the end of a sentence), language, the board (connection, WiFi, firmware, its settings, wake word, volume; it was the Yoru page until 2026-10-21) and about |

The tray icon shows the last notification, a "talk" button and do-not-disturb. The first run has four steps: connect Yoru, pick the brain (with Yoru's voice as an optional part), connect a first service, say what matters to you (the first memory).
